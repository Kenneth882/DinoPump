# Fresh checkout, startup and recovery

Ticket #22 follows §7–13 and AC-10/12/13/14/15/17/18. Use the pinned
Node 24.21.0 and pnpm 10.34.5 with Docker Compose. The local database image is
PostgreSQL 18.6 (`postgres:18.6-alpine3.24`). Start with the complete
[README setup](../README.md#local-setup), including `pnpm build:shared` before
migrations and the separate [worker template](../.env.commentary.example).
No global TypeScript, Next.js or provider key is needed. See the
[actual rehearsal results](validation/ticket-22-setup.md).

## Configuration ownership

| Process    | Local configuration                                                                                                   | Hosted demo configuration                                                                                                                                              |
| ---------- | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PostgreSQL | Root `.env`: `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `POSTGRES_PORT`                                     | Dedicated Supabase project, persistent managed storage; operator secret kept off apps                                                                                  |
| Game       | Root `.env`: `DATABASE_URL`, `GAME_SERVER_PORT`, `WEB_ORIGIN`                                                         | Restricted runtime URL, `DATABASE_SCHEMA`, verified `DATABASE_SSL_CA_FILE`, `GAME_SERVER_HOST=0.0.0.0`, Render `PORT`, `NODE_ENV=production`, exact HTTPS `WEB_ORIGIN` |
| Web        | Root `.env` in development: `GAME_SERVER_ORIGIN`                                                                      | `GAME_SERVER_HOSTPORT` at both build and runtime, `NODE_ENV=production`, Render `PORT`; no database/provider credentials                                               |
| Worker     | Only `.env.commentary`: restricted `COMMENTARY_DATABASE_URL`, optional `COMMENTARY_HEALTH_PORT` and provider settings | Omitted from the approved two-service demo; the current local worker commands are not a hosted worker deployment recipe                                                |

`DATABASE_URL` in local development is the Docker bootstrap operator. Hosted
apps must use the restricted login from the [demo runbook](demo-deployment.md).
Do not put either URL in `NEXT_PUBLIC_*`. Session secrets are generated by the
server; no static signing key or Supabase browser key is required. Keep `.env*`
secret files mode 600 and ignored; never source them as shell scripts. URL-encode
passwords. Changing Docker's bootstrap password after a volume exists does not
change the stored PostgreSQL password: rotate deliberately, never reset the volume.

`pnpm dev` builds/watches shared packages, game and web. Run `pnpm worker` in
another terminal after role provisioning. The worker may start with narration
disabled and still be ready; missing credentials leave complete authored news.

## Compiled local startup

Stop development watchers before starting compiled services on the same ports.
From the root, with `.env` and `.env.commentary` prepared:

```sh
pnpm db:up
pnpm db:check
pnpm build:shared
pnpm db:migrate
pnpm db:worker-role
# This default matches the local .env example. Override at BOTH build and start
# if the game port changes; Next.js freezes the Socket.IO rewrite at build time.
GAME_SERVER_ORIGIN=http://127.0.0.1:3001 pnpm build
```

Run each application in a separate terminal at the repository root:

```sh
pnpm --filter @dinopump/game-server start
```

```sh
GAME_SERVER_ORIGIN=http://127.0.0.1:3001 pnpm --filter @dinopump/web start
```

```sh
pnpm --filter @dinopump/commentary-worker start
```

For a local HTTP-only rehearsal leave game `NODE_ENV` unset, as in `.env.example`.
The compiled Next.js server itself runs in production mode and does not load the
root `.env`. For secure cookies and HTTPS, use `pnpm test:staging-local --smoke`
or the hosted runbook; do not set production game cookies on plain local HTTP.

Readiness checks, after database → migrations → game → web/worker startup:

```sh
curl --fail http://127.0.0.1:3001/readyz
curl --fail http://127.0.0.1:3000/api/market-baseline
curl --fail http://127.0.0.1:3002/readyz
```

The baseline endpoint proves web-to-game connectivity, not database ownership.
Game readiness must also pass. Worker readiness follows its first successful
poll. Test with two separate browser profiles so cookies represent two guests.
Create/join, ready, trade, disconnect/reconnect, wait for nine events and results;
verify the fictional-currency notice. Automated commands are listed below.

## Shutdown, restart and failures

For a planned stop, finish the current demo round and tell guests about maintenance.
Stop web traffic, then send Ctrl-C/SIGTERM to game and worker and wait for exit.
The game stops scheduling, disconnects sockets and closes its store/pool. Then
`pnpm db:stop` preserves the named volume. Restart PostgreSQL, confirm migrations,
then start exactly one game, check `/readyz`, start web and worker, and reconnect
an existing guest. Do not use `docker compose down --volumes`, drop schemas,
truncate history or clear ownership locks as routine setup/recovery.

An unexpected stop does not extend deadlines. The next owner verifies committed
history, rebuilds mutable projections, applies overdue events in order and settles
once if close has passed before accepting commands. A pending browser order keeps
its original request ID/payload; retries must resolve the original outcome.

On database/ownership loss the old game fails closed. Keep traffic off, restore
connectivity and restart the game to acquire ownership anew. A second game must
fail to start while the first owns the same schema. Do not force-unlock it.
On integrity abort, preserve evidence; no winner is invented. Existing frozen
results remain immutable. A host may use the normal return-to-lobby action after
a verified terminal state. Optional worker failure does not stop gameplay.
See [operational diagnostics](operations.md#recovery) and
[owned recovery](database.md#recovery-and-projection-rebuilding).

## Backup and restore rehearsal

PostgreSQL stores sessions, frozen configuration, complete event batches, receipts,
news and results. Render application disks are disposable; do not store these on
an app filesystem. There is no automatic history/results pruning. Returning to the
lobby retains prior results; access still requires an unexpired participant session
(default lifetime 24 hours). Backup retention and result retention are separate.

For local backup, stop game/worker writes and use the configured Compose project.
The following produces a private custom-format archive without putting a URL or
password in command arguments. `pg_dump` comes from the pinned database image:

```sh
umask 077
mkdir -p .private-backups
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom --no-owner --no-acl' > .private-backups/dinopump.dump
docker compose exec -T postgres pg_restore --list < .private-backups/dinopump.dump > .private-backups/archive-list.txt
```

Keep `.private-backups` ignored and encrypted when exported. An archive listing
only proves readability. To rehearse restore, use an **empty, separately authorized
disposable database**, never the source. In the isolated local checkout rehearsal,
create `dinopump_restore_check` in its synthetic PostgreSQL instance:

```sh
docker compose exec -T postgres sh -c 'createdb -U "$POSTGRES_USER" dinopump_restore_check'
docker compose exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d dinopump_restore_check --no-owner --no-acl --exit-on-error' < .private-backups/dinopump.dump
```

No `--clean`/drop command is needed. Roles/passwords are not in this archive. The
local instance already has `dinopump_commentary` from migrations; on a new cluster
create that NOLOGIN permission group before restoring, then reapply the restricted
worker grants using the reviewed migration definitions. Because `--no-acl` omits
revocations too, restore is not ready to serve until PUBLIC function access is
revoked. For this local `public` schema rehearsal, run:

```sh
docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d dinopump_restore_check' <<'SQL'
REVOKE ALL ON ALL FUNCTIONS IN SCHEMA public FROM PUBLIC;
GRANT USAGE ON SCHEMA public TO dinopump_commentary;
GRANT EXECUTE ON FUNCTION public.claim_commentary(bigint,uuid), public.finish_commentary(uuid,uuid,jsonb,bigint) TO dinopump_commentary;
SQL
```

Use the actual source schema for a hosted restore. Runtime roles/grants must
also be recreated separately. Stop the source game before connecting a game to the
restored target, set only the target database in the private environment, and
verify readiness, replay and frozen results. Record source/target, archive checksum,
backup time, restored round IDs, comparison results, elapsed time and any lost
commits. A restore can only recover commits present at backup time.

The [hosted plan](demo-deployment.md) requires a separate target and approval for
its costs. Supabase backup existence or a successful local restore does not prove
managed restore compatibility. Do not promise a recovery time or loss window until
measured and approved; daily backups can lose changes since their snapshot.

## Isolated validation

```sh
pnpm check
pnpm db:verify
pnpm exec playwright install chromium
pnpm test:e2e
pnpm test:staging-local --smoke
```

Stop manual dev/compiled processes first, including the worker on port 3002
(the worker process test uses that port). Run suites serially, with
`COMPOSE_PROJECT_NAME` unset in both the shell and `.env` so the dedicated test
project remains isolated. Database/browser suites create synthetic PostgreSQL on 55433 and
remove only their disposable test container. Browser services use 3100/3101;
load uses 55434; local production ingress uses 55435 and ephemeral app ports.
They do not consume the development `.env` database. `db:verify` includes real
crash/restart and ownership tests (AC-10/12/14/15); browser suites include two
sessions, 360px and a no-key round (AC-13/17/18), using accelerated test time.
The staging smoke checks production HTTPS/proxy/cookies; it is not a full round.
It also needs the `openssl` CLI with `req -addext` support (validated here with
OpenSSL 3.5.6); check `openssl version` before running it. This is a local
test-certificate dependency, not a hosted runtime dependency.

For real ten-minute evidence run `pnpm test:load`; for the unchanged full capacity
gate run `pnpm test:load --sustained` or the approved hosted staging adapter.
Those workload/latency failures remain tracked in [#21 evidence](validation/ticket-21-acceptance.md).
A smaller demo audience does not change AC-18 or establish full MVP acceptance.
